# neo3ds가 구형 3DS에서 네오지오 게임을 풀스피드로 돌리는 방법

[English](TECHNICAL.md)

README의 "64MB 모드와 최적화"를 길게 풀어 쓴 문서입니다. 구형 3DS가 주는 자원, 시간과 메모리가 어디에
쓰이는지, 해 봤다가 버린 것까지 적었습니다. 따로 적지 않은 수치는 모두 실제 구형 3DS에서 잰 값입니다.

## 예산

| | 구형 3DS | 네오지오 게임 |
|---|---|---|
| CPU | ARM11 MPCore 268MHz × 2 | 68000 12MHz + Z80 4MHz |
| 앱이 쓸 수 있는 메모리 | 기본 모드 64MB | KOF99 / 메탈슬러그 3: 스프라이트 64MB + 사운드 16MB + 프로그램 8MB |
| 저장소 | RomFS를 통한 SD 카드 | – |
| 프레임 | 16.7ms (LCD 59.8Hz) | 59.185Hz |

나머지 설계는 세 가지 조건에서 나왔습니다.

- **메모리.** 큰 게임은 풀면 90MB쯤 됩니다. 80MB 모드는 더 들어가지만, 게임을 켜고 끌 때마다
  시스템이 HOME 메뉴를 내렸다 다시 띄워서 오래 걸립니다. 96MB 모드는 HOME 메뉴 프로세스가
  크래시했습니다. 그래서 기본 64MB 모드(힙 58MB + 화면용 linear 메모리 2MB)를 목표로 했습니다.
- **SD에서 읽어 오는 방식은 불가.** 구형 3DS의 RomFS는 순차 읽기 약 7.5MB/s, 랜덤 읽기는 초당
  30~40회뿐이라 스프라이트 타일을 그때그때 읽어 올 수 없습니다. 전부 RAM에 있어야 합니다.
- **두 번째 코어는 공짜가 아니다.** 시스템 서비스(그래픽 GSP, 사운드 DSP)가 코어 1에서 돌고,
  앱은 그중 일부만 씁니다(`APT_SetAppCpuTimeLimit(80)`). 코어 1이 바쁠 때 서비스를 거치는 호출은
  몇 ms씩 기다릴 수 있습니다.

## 출발점

에뮬레이션 핵심부는 GP2X 시절 네오지오 에뮬레이터 [gngeo](https://github.com/pepone42/gngeo)와
그 ARM 어셈블리 CPU 코어 Cyclone(68000), DrZ80(Z80)입니다. 둘 다 빠르지만, 메모리 접근 때 인자
레지스터의 상위 비트를 지우지 않고 C 함수를 부릅니다. 그래서 모든 콜백은 `unsigned int`로 받아
직접 마스킹합니다. 이식에서 가장 큰 버그가 여기서 나왔습니다.

PC 쪽은 C# 변환기입니다. MAME 롬셋 zip을 읽어 해독하고 CIA를 만듭니다. 보호 방식(CMC42/CMC50
스프라이트·사운드 암호화, SMA와 PVC 프로그램 암호화, PCM2, KOF2002형 프로그램 섞기, SVC Chaos Plus
해적판)은 모두 MAME를 따라 PC에서 풉니다. 3DS는 해독에 메모리도 시간도 쓰지 않습니다.

## 메모리: 58MB 힙에 64MB 스프라이트 넣기

- **블록 압축.** 스프라이트 롬을 4KB 블록으로 잘라 블록마다 zstd 레벨 19로 압축합니다.
  KOF98 64MB 기준 LZ4 HC 32.3MB, zstd 22.1MB (16KB 블록이면 19.9MB, 사전은 효과 없음).
  KOF99 64MB → 19.6MB.
- **8MB 블록 캐시.** 블록 안의 타일을 그릴 때 슬롯에 풀어 둡니다(라운드 로빈 교체). 실기에서는
  복잡한 장면에서도 캐시 미스가 초당 몇 번 수준입니다.
- **투명 표.** 변환기가 타일마다 2비트를 저장해서, 완전히 투명한 타일은 블록을 건드리지 않고 건너뜁니다.
- **결과.** KOF99와 메탈슬러그 3이 58MB 중 약 53.5MB를 씁니다.

## 두 코어

```
코어 0: | 68k + Z80 + 타이머, 프레임 N+1 (스캔라인 264개 단위) | 스냅샷 |
코어 1:                        | 사운드 N | 프레임 N을 프레임버퍼에 그리기 |
```

- **코어 0**은 68000, Z80, 타이머를 스캔라인 단위로 번갈아 돌립니다(프레임당 264번). 프레임이 끝나면
  그리기에 필요한 상태(비디오 RAM 0x10c00바이트, 팔레트, 프레임 카운터)를 복사해 코어 1에 넘깁니다.
- **코어 1**은 그 프레임의 소리를 합성하고 화면을 그리는 동안, 코어 0은 벌써 다음 프레임을 돌립니다.
  화면과 소리는 1프레임 늦게 나옵니다.

### 사운드 칩을 둘로

YM2610은 같은 코드의 복사본 두 개로 에뮬레이션합니다.

- 코어 0의 **제어용 칩**은 Z80의 쓰기를 바로 받습니다. 사운드 드라이버가 타이머, 인터럽트, 상태를
  계속 확인하기 때문에 이쪽은 정확하고 제때여야 합니다.
- 모든 쓰기는 기록도 됩니다. 프레임이 끝나면 기록이 코어 1의 **합성용 칩**으로 넘어가고, 합성용 칩이
  재생하면서 ndsp로 보낼 샘플을 만듭니다.
- ADPCM "재생 끝" 플래그는 합성용 칩에만 있어서 상태 읽기는 그쪽 값을 씁니다. Z80이 방금 지운
  플래그는 그 쓰기가 재생될 때까지 가립니다.
- 기록에는 쓰기마다 스캔라인이 남고, 코어 1은 그 위치까지 합성한 뒤 쓰기를 적용합니다. 예전에는
  한 프레임의 쓰기를 프레임 시작에 한꺼번에 적용해서, 빠른 음높이 변화가 60Hz 계단으로 바뀌었습니다
  (메탈슬러그 3 컨티뉴 카운트다운은 SSG 음높이를 한 프레임에 여러 번 바꿉니다).

## GPU 없이 그리기

초기 버전은 citro3d로 화면을 늘리고 돌렸습니다. GPU 단계마다 코어 1의 GSP 서비스를 거쳐서 거의 매
프레임 vblank를 놓쳤습니다. 다 그린 화면을 CPU로 회전 복사하면 코어 1에서 7.5ms(코어 0에서는
4.3ms)가 들었습니다. 그래서 지금은 상단 화면 프레임버퍼에 바로 그립니다. 프레임버퍼는 회전된
형태(240픽셀짜리 세로줄이 이어지는 형태)라서, 오른쪽으로 한 칸은 +240, 아래로 한 줄은 -1입니다.

- `gspPresentBuffer`로 **트리플 버퍼**를 쓰고, 반환값으로 지금 화면에 나간 버퍼를 추적합니다.
- **캐시 정리**는 `svcStoreProcessDataCache`를 직접 부릅니다. `GSPGPU_FlushDataCache`는 코어 1이
  바쁠 때 5.6ms가 걸렸습니다.
- TV처럼 **보이는 304×224만** 그립니다(양 끝 8열은 게임이 깨끗하게 그리지 않는 오버스캔 영역).

### 스프라이트 렌더러

네오지오에는 배경 레이어가 없습니다. 고정 글자 레이어를 빼면 전부 스프라이트이고, 폭 16픽셀,
높이 최대 512줄에 하드웨어 축소가 있습니다. 렌더러는 MAME의 스캔라인 단위 로직을 따르면서 빠른
경로를 더했습니다.

- **축소 없는 스프라이트**(대부분)는 타일 단위로 그려서, 타일 찾기를 줄마다가 아니라 16줄마다 한 번 합니다.
- **불투명 묶음.** 타일 한 줄의 8픽셀 반쪽마다 검사해서, 완전히 투명하면 건너뛰고 완전히 불투명하면
  ARM 어셈블리 블록이 씁니다(시프트한 레지스터와 `and` 한 번으로 팔레트 오프셋을 구하고, `ldr`과
  세로줄 간격의 `strh`). KOF98과 메탈슬러그 2에서는 반쪽의 90% 이상이 완전히 불투명했습니다. 같은
  생각을 C로 쓴 버전은 GCC가 인덱스 8개를 스택에 흘려서 오히려 느렸습니다.
- **가로로 축소된 줄**은 줌 단계 16개와 좌우 반전마다 컴파일 때 펼쳐 둔 직선 코드(`put_row_zoom_k`)로
  그립니다. 줌 아웃된 사무라이 쇼다운 5 스페셜 프레임이 12.1ms에서 7.0ms가 되어 풀스피드가 됐습니다.

## 프레임 페이싱

메인 루프는 `gspWaitForVBlank()`로 vblank를 기다렸는데, 이 함수는 항상 *다음* vblank를 기다립니다.
그래서 17ms 걸린 프레임은 vblank 하나를 놓치고 그다음 것까지 기다려 33ms가 됐습니다. 메탈슬러그 3의
무거운 장면에서 두 코어 모두 평균 약 14.5ms였는데도 53~55fps가 나온 이유입니다. 가끔 느린 프레임이
한 프레임을 통째로 잃었습니다.

`gspWaitForEvent(GSPGPU_EVENT_VBlank0, false)`는 vblank가 이미 지났으면 바로 돌아옵니다. 이제 조금
늦은 프레임은 조금만 늦고, 다음 프레임이 따라잡습니다.

자동 프레임 스킵도 해 봤습니다. 루프가 밀리면 다음 프레임은 에뮬레이션과 사운드만 하고 그리지
않는 방식입니다. 게임 속도는 더 일정했지만 스크롤이 눈에 띄게 튀어서, 약간 느려지는 것보다 나빠
보였습니다. 그래서 뺐습니다.

## 사운드 드라이버의 대기 루프 건너뛰기

메탈슬러그 2·X·3의 사운드 드라이버는 Z80 시간의 약 절반을 이 루프에서 보냅니다.

```
s:    ld   a,(hl)      ; 7사이클  (hl = $F801, 타이머 인터럽트가 올림)
s+1:  and  a           ; 4
s+2:  jp   z,s         ; 10
```

이 루프 안에서는 인터럽트가 올 때까지 아무것도 바뀌지 않고, 인터럽트는 슬라이스 사이에만 옵니다.
그래서 슬라이스가 이 루프에서 시작하고, 바이트가 아직 0이고, 대기 중인 인터럽트가 없으면 Z80을
돌리지 않습니다. 예전 시도(다음 인터럽트까지 Z80을 멈추기)는 소리가 달라졌기 때문에, 이번에는 CPU를
DrZ80이 돌았을 때와 똑같은 상태로 둡니다.

- DrZ80은 남은 사이클이 0 이상인 동안 명령을 실행합니다. 그래서 루프의 사이클 비용을 따라가며
  멈췄을 명령을 찾아 PC를 그 위치로 옮깁니다.
- A = 0, F는 `and a`(또는 `or a`)가 0일 때 남기는 값으로 DrZ80 형식에 맞춰 둡니다.
- 루프는 게임별 주소가 아니라 바이트 패턴으로 찾습니다.

첫 버전은 PC를 그대로 뒀습니다. 그랬더니 데모 화면 2400프레임 뒤 Z80의 YM2610 쓰기가 건너뛰기 없이는
50,992번, 건너뛰기로는 50,928번이었습니다. 인터럽트에서 돌아오는 위치가 루프 안에서 조금씩 달라져
타이밍이 갈라진 것입니다. PC를 옮기자 메탈슬러그 3과 2 모두 두 빌드의 쓰기 횟수와 Z80 RAM 체크섬이
같아졌습니다(데모 화면은 입력이 없어서 실행이 반복 가능합니다).

## 측정값

메탈슬러그 3의 복잡한 장면(헤비머신건, 폭발), 실기, 페이싱 수정 전, 프레임당 ms:

| 코어 0 | | 코어 1 | |
|---|---|---|---|
| 68000 | 10.45 | 사운드 합성 | 3.63 |
| Z80 | 3.22 | 그리기 (스프라이트 11,510줄) | 10.92 |
| 타이머 | 0.53 | | |

여기까지 온 과정 (KOF98 / 메탈슬러그 2):

| 버전 | 결과 |
|---|---|
| 단일 코어 | KOF98 29.9fps (CPU 7.6 + 그리기 10.4 + 복사 4.3 + 사운드 4.6ms) |
| 코어 1에서 citro3d 또는 CPU 회전 복사 | 30~50fps (GSP 대기, 회전 복사) |
| 회전된 프레임버퍼에 바로 그리기, 트리플 버퍼 | 59fps, 찢어짐 없음 |
| ARM 어셈블리 묶음, 사운드 합성을 코어 1로 | 메탈슬러그 2 플레이 가능 |

메탈슬러그 2·X·3은 원래 아케이드 기판에서도 가장 복잡한 장면에서 느려집니다. neo3ds도 같은 곳에서
프레임이 떨어지고, PC 에뮬레이터도 마찬가지입니다.

## 버그를 찾은 방법

- **MAME를 기준으로.** 공식 MAME를 화면 없이 돌리면서 Lua 스크립트로 68000의 사운드 명령 포트와
  Z80의 YM2610 포트를 엿보면, 모든 명령과 레지스터 쓰기 기록이 나옵니다. neo3ds의 같은 기록과
  명령 단위로 비교해서 사운드 롬 배치 오류와 위의 사운드 타이밍 버그를 찾았습니다. 코인을 넣고
  타이머가 다 될 때까지 두는 스크립트로, 직접 플레이하지 않고도 컨티뉴 화면까지 갑니다.
- **결정성 검사.** 입력이 없으면 에뮬레이션이 반복 가능하므로, 정해진 프레임의 체크섬으로 최적화가
  무언가를 바꿨는지 알 수 있습니다.
- 빠른 실행에는 **Azahar**(3DS 에뮬레이터)를 씁니다. ARM11의 메모리 타이밍을 흉내 내지 않고
  명령 수를 세는 방식이라, 코드의 일 양을 비교하는 데는 좋지만 절대 속도와는 다릅니다.
